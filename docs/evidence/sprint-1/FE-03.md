## Implemented

| File | Layer / owner | Content |
|---|---|---|
| `src/Lunar.Desktop/Shell/IslandLayout.cs` | Desktop (FE) | Pure sizing rules in DIPs: idle fixed 160×44; expanded min 380×320, max = work area minus 8 DIP edge margins and the top offset, minimum shrinks if the work area is smaller (never below the pill); `Fit` clamps measured content into the limits and treats NaN, infinite and negative sizes as zero. |
| `src/Lunar.Desktop/Shell/IslandPositionController.cs` | Desktop | Now also sizes the window: measures the content, fits it into the limits for the current layout, applies Min/Max/Width/Height, then places it (FE-05) using that size. Re-runs on layout change, content change, display/taskbar change and DPI change. Constructor takes the `IslandViewModel`. |
| `src/Lunar.Desktop/Shell/IslandWindow.xaml(.cs)` | Desktop | `ViewContentChanged` event, internal `MeasureContent` (forces a real measure of the pill tree, because WPF otherwise reuses a cached measurement for unchanged ancestors) and `ApplySize`; corner radius is the pill token while idle and the panel token (24) in any expanded layout, through a style trigger. |
| `src/Lunar.Desktop/Shell/IslandViewModel.cs` | Desktop | `IsExpandedLayout` (true in every state except Idle, including both animations, so the window never shrinks under content still being shown). |
| `src/Lunar.Desktop/App.xaml.cs` | integrator | Passes the view model to the controller. |
| Tests | tests (FE) | `IslandLayoutTests.cs` (27), existing controller tests updated for the new parameter, `IslandViewModelTests` notification list. |

Why a measured size and not `SizeToContent`: the size is needed before the window is shown (to place it without a jump), and the same computed size feeds the placement rules; the measurement is explicit and unit-testable.

Development findings kept visible:
1. The first version of the content test failed: after replacing huge content with none, the window stayed at its maximum. WPF returned a cached `DesiredSize` for the pill because only a deep descendant had been invalidated. `MeasureContent` now invalidates the whole (small) pill tree before measuring.
2. The corner-radius test failed at first because tests do not run `App.xaml`, so the shape token was unresolved (radius 0). The test now loads `Spacing.xaml` into the window; in the app the token comes from `App.xaml`.

Automated cases: idle fixed regardless of content; expanded default and growth; cap at work area minus margins; invalid content sizes; tiny and absurd work areas; argument validation; **a DPI matrix** (96/120/144/192 DPI on 1920×1080, 1366×768, 1280×720, 1024×600, 800×600 and 3840×2160; idle and expanded; empty, medium and 5000×5000 content) asserting that the physical rectangle lies inside the work area and that `PlaceTopCenter` did not have to shrink it; real WPF windows: idle size, growth on expand, still large while collapsing, back to idle, recentered after resizing, content measured and clamped, idle ignores oversized content, small work area caps the expanded window, corner radius 999/24 by state; `IsExpandedLayout` follows the state.
