Development failures kept visible:
1. `PostMessage` of `WM_SETTINGCHANGE` and `WM_DPICHANGED` failed with Win32 error 1159 (`ERROR_MESSAGE_SYNC_ONLY`); Windows only delivers them synchronously. The tests now use `SendMessage` for the work-area message.
2. Even with `SendMessage`, `WM_DPICHANGED` from another sender never reached the window procedure (observed through the test; the listener thread was made per-monitor aware first, which did not change it). It cannot be simulated, so a dedicated test calls the window procedure directly with the message. This proves the mapping from message to notification only, **not** that Windows sends `WM_DPICHANGED` to this hidden window on a real DPI change.
3. A test assertion compared a DPI context to the pseudo-handle `-1`; Windows returns the real handle. Fixed to compare handles before and after.
4. A race in my first version would have crashed the process if the startup wait object was disposed before the listener thread's final signal; found in review before running, fixed by not disposing it.

Real-host checks:
- A scratch probe (outside the repo, a DPI-unaware console process) read the displays through the adapter: one display, `\\.\DISPLAY1`, primary, bounds 0,0 1920×1080, work area 0,0 1920×1020, 120 DPI ([result](be-08-20261103/real-host-displays.json)). The provider reports physical pixels even for an unaware process.
- `IslandPlacement.PlaceTopCenter(160×44 DIP, offset 8)` on that display gives 860,10 200×55, **identical** to the geometry measured on the real FE-02 window (left 860, top 10, 200×55) in the earlier smoke.
- An independent API (`GetSystemMetrics`) agrees with the adapter on the primary display size (automated test).
